Versi: 1.0 (Final untuk development MVP) · Status: Siap dikerjakan · Bahasa: Indonesia
1. Ringkasan Produk
Item
Keterangan
Nama produk
JastipOps
Deskripsi
Aplikasi manajemen operasional jasa titip (jastip) berbasis web: REST API + Back Office Web App
Masalah
Pencatatan di Excel/WhatsApp rawan salah hitung, data pelanggan tercecer, status barang & pembayaran tidak jelas, margin tidak terpantau
Tujuan
Satu sistem terpusat untuk pelanggan, trip/batch, order, pembayaran, belanja lapangan, pengiriman, dan laporan margin
Platform
Web responsif (desktop untuk Owner/Admin, mobile-first untuk Shopper)
1.1 Persona Pengguna
Owner: kontrol penuh, melihat modal, margin, dan laporan.
Admin Order / CS: input pelanggan & order, verifikasi pembayaran, input resi. Tidak melihat modal dan profit.
Shopper: bekerja di toko lewat HP. Hanya melihat daftar belanja dan mengubah status barang.

6. Aturan Bisnis & Rumus
Notasi: FP harga asing per unit, SR sell_rate snapshot, CR cost_rate, fee fee per unit, qty jumlah.
harga_jual_idr per unit = round_up(FP × SR, pembulatan_trip).
total_item = (harga_jual_idr + fee) × qty. Item berstatus OUT_OF_STOCK bernilai 0 pada tagihan (nilai historis tetap tersimpan).
subtotal_items = Σ total_item.
total_tagihan = subtotal_items + ongkir − diskon.
total_dibayar = Σ pembayaran sah (DP + pelunasan) − Σ refund yang dikembalikan.
sisa_tagihan = total_tagihan − total_dibayar (negatif berarti kelebihan bayar).
Profit item = total_item − (harga_beli_aktual_asing × qty × CR). Jika harga beli aktual kosong, pakai FP sebagai estimasi.
Rincian profit: fee = fee × qty; selisih kurs = FP × qty × (SR − CR); selisih harga = sisanya (pembulatan, selisih harga beli aktual).
Semua perhitungan dijalankan di service backend dalam satu transaksi database dan dihitung ulang setiap perubahan item/pembayaran/ongkir/kurs. Nilai total disimpan (denormalisasi) untuk performa, dengan pengecekan konsistensi harian.
Refund otomatis (acceptance criteria #2): saat item → OUT_OF_STOCK, total tagihan dikurangi nilai item tersebut; jika total_dibayar > total_tagihan, order berstatus OVERPAID dan muncul tugas "Refund Rp X". Tidak ada baris pembayaran yang diubah.
Order CANCELLED memiliki total tagihan 0 dan nilai historis disimpan pada snapshot.
7. State Machine
Item: PENDING → PURCHASED → ARRIVED; PENDING/PURCHASED → OUT_OF_STOCK. Pembalikan PURCHASED → PENDING diizinkan untuk Shopper dalam 10 menit (koreksi salah centang) dan selanjutnya hanya Owner/Admin. OUT_OF_STOCK → PENDING hanya Owner (barang ditemukan kembali) dan mencatat audit.
Order: DRAFT → CONFIRMED → PROCESSING → SHIPPED → DELIVERED; CANCELLED dari status mana pun sebelum SHIPPED.
PROCESSING otomatis ketika ada item pertama yang PURCHASED.
SHIPPED mensyaratkan resi terisi dan tidak ada item PENDING.
DELIVERED manual (atau otomatis bila ada setting).
Trip: OPEN → SHOPPING → SHIPPING → COMPLETED.
Setiap transisi tidak valid menghasilkan 409 Conflict dengan kode error INVALID_STATE_TRANSITION.

Semua tabel memiliki id UUID, created_at, updated_at. Tabel yang dapat dihapus lunak memiliki deleted_at.

10. Alur Pengguna Utama
Persiapan: Owner membuat trip (kurs, fee default) → status OPEN.
Order masuk: Admin mencari/menambah customer → membuat order & item → kirim ringkasan invoice ke pelanggan → catat DP → order CONFIRMED.
Belanja: Owner mengubah trip ke SHOPPING → Shopper membuka daftar belanja di HP → centang "Dibeli" atau "Kosong" → tagihan otomatis menyesuaikan.
Penagihan: Admin melihat order PARTIAL/OVERPAID → catat pelunasan atau refund.
Pengiriman: Admin input ongkir & resi → order SHIPPED → DELIVERED → trip COMPLETED.
Evaluasi: Owner melihat dashboard profit per trip.
11. Kebutuhan Non-Fungsional
Aspek
Persyaratan
Performa
Pencarian customer p95 < 300 ms (data hingga 50.000 customer); daftar order p95 < 500 ms; shopping list 1.000 item < 1 detik
Keamanan
HTTPS wajib; CORS whitelist; rate limit; header keamanan (Helmet/secure-headers); proteksi SQL injection via Prisma; validasi upload (tipe & ukuran, rename acak); sanitasi input; secret di environment variable
Privasi
Data pelanggan (WA, alamat) dilindungi RBAC; log tidak memuat password/token; mematuhi UU PDP (hak koreksi & penghapusan atas permintaan, dilakukan lewat anonimisasi)
Ketersediaan
Target 99,5%; backup database harian dengan retensi 14 hari dan uji restore tiap kuartal
Integritas
Transaksi database untuk operasi keuangan; optimistic locking (updated_at/versi) untuk mencegah dua staf menimpa data yang sama
Skalabilitas
Dirancang untuk 1 bisnis, ±200 order/trip dan 20 trip/tahun; mudah diperluas
UX
Responsif; Shopper view mobile-first; mode gelap tidak wajib; semua teks dalam Bahasa Indonesia; format Rupiah Rp 1.250.000
Aksesibilitas
Kontras memadai, target sentuh ≥ 44 px untuk tampilan Shopper
Kualitas
Cakupan test unit ≥ 80% pada service keuangan; E2E untuk alur order → bayar → belanja → refund
Dokumentasi
OpenAPI, README setup, .env.example, panduan deploy

15. Asumsi & Pertanyaan Terbuka
Asumsi v1: satu mata uang per trip; satu bisnis per instalasi; pembayaran hanya dalam Rupiah; DP minimum default 50% untuk pelanggan Wajib DP; pembayaran dicatat manual berdasarkan bukti transfer.
Perlu konfirmasi Owner (tidak menghalangi mulai development, sudah ada default):
Apakah fee berupa nominal tetap, persentase, atau keduanya? (default: keduanya didukung per trip)
Apakah pembayaran harus diverifikasi Owner sebelum dihitung lunas? (default: tidak, diaktifkan lewat setting)
Apakah perlu invoice PDF bermerek di v1? (default: teks siap salin dulu)
Berapa jumlah staf dan Shopper aktif, serta apakah Shopper memakai HP pribadi? (menentukan kebutuhan mode offline)
Apakah ada pajak/bea masuk yang ditagihkan ke pelanggan? (default: tidak ada; dapat ditambah sebagai biaya tambahan di v1.1)
Lampiran A: Daftar Kode Error
VALIDATION_ERROR, UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, DUPLICATE_PHONE, TRIP_CLOSED, INVALID_STATE_TRANSITION, PAYMENT_ALREADY_VOID, LAST_OWNER_PROTECTED, DP_REQUIRED, RATE_LIMITED, INTERNAL_ERROR.
Lampiran B: Contoh Perhitungan
Trip Bangkok: SR = 465, CR = 452, pembulatan Rp 100. Item: harga 890 THB, qty 2, fee Rp 25.000/unit.
Harga jual/unit = 890 × 465 = 413.850 → dibulatkan Rp 413.900
Total item = (413.900 + 25.000) × 2 = Rp 877.800
Modal = 890 × 2 × 452 = Rp 804.560
Profit = 877.800 − 804.560 = Rp 73.240 (fee Rp 50.000 + selisih kurs Rp 23.140 + pembulatan Rp 100)
Jika pelanggan sudah DP Rp 500.000 lalu barang kosong: tagihan menjadi 0, status OVERPAID, refund Rp 500.000, riwayat DP tetap utuh.
